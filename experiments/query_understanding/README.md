# 관심 질의 해석 + 연구실 검색 실험 v1 (2026-10-11)

홈에서 입력한 관심 문장("나는 로봇은 싫은데 컴퓨터 아키텍처는 좋아요")을 연구실 검색으로 연결하는 방법 비교. 앱에는 반영하지 않았다.

## 파일

| 경로 | 내용 |
|---|---|
| `queries.json` | 질의 39개 (단순 6, 다른 표현 8, 부정 8, 복합 용어 7, 다중 관심 6, 약한 부정 4). 정답 = 연구실 프로필의 `primary` 주제 개념 |
| `rule_interpreter.py` | 규칙 질의 해석(좋아함/싫어함 분리, 구절 유지) |
| `build_papers.py`, `papers_app.jsonl` | 팀원 카탈로그 페이지에서 앱 교수의 대표 논문 514편(51개 연구실) 추출 |
| `query_understanding_v1.ipynb`, `make_notebook.py` | Kaggle T4 노트북(생성 스크립트 포함) |
| `evaluate.py` | 지표 계산. A(현재 앱)는 로컬에서 직접 계산 |
| `analyze_hybrid.py` | 사후 분석: 현재 사전 검색 + 해석, 순위 융합 |
| `V1/` | 실행 결과(`ranks_v1.json`, `interp_v1.json`, `settings_v1.json`, 지표) |

## 방법

| 이름 | 질의 처리 | 검색 |
|---|---|---|
| A | 개념 사전(현재 앱) | 규칙 점수 |
| B | 없음(문장 전체) | bge-m3 임베딩, 연구실 문서 중 최대 유사도 |
| C | 규칙으로 좋아함/싫어함 분리, 구절 유지 | 구절별 임베딩. 점수 = 좋아함 평균 z − λ·싫어함 최대 z |
| D | Qwen2.5-7B가 JSON으로 분리 | C와 같음 |

숫자 0/1은 연구실 문서(0: 프로필, 1: 프로필 + 대표 논문 제목·초록 500자). λ는 0, 0.5, 1, 2.

## 결과 (질의 39개, 연구실 56개, 상위 5개 기준)

P@5(상위 5개 중 정답 비율). 부정 질의 12개는 viol(싫다고 한 주제의 연구실이 상위 5개에 하나라도 든 질의 비율).

| 방법 | 단순 | 다른 표현 | 복합 용어 | 다중 관심 | 부정 | 약한 부정 | 전체 | viol |
|---|---|---|---|---|---|---|---|---|
| A 현재 앱 | 1.00 | 0.53 | 0.66 | 0.83 | 0.53 | 0.75 | 0.69 | 0.75 |
| B1 문장 전체 임베딩 | 0.53 | 0.55 | 0.49 | 0.50 | - | - | 0.47 | 0.75 |
| C1 (λ=1) | 0.77 | 0.62 | 0.51 | 0.77 | 0.68 | 0.65 | 0.66 | 0.08 |
| D1 (λ=1) | 0.77 | 0.65 | 0.51 | 0.80 | 0.65 | 0.55 | 0.66 | 0.17 |
| 사후: A + 규칙 해석 | 1.00 | 0.53 | 0.66 | 0.83 | 0.85 | 0.85 | 0.77 | 0.17 |
| 사후: 순위 융합(A+규칙 해석, C1) | 1.00 | 0.72 | 0.71 | 0.90 | 0.85 | 0.90 | 0.84 | 0.08 |

- 임베딩만 쓰는 방법(B, C, D)은 현재 앱(A)보다 전체 P@5가 낮다. 질의별로는 A가 이긴 것이 18건, C1이 이긴 것이 13건, 비긴 것이 8건.
- 부정 질의의 큰 개선은 "싫다고 한 구절을 질의에서 빼는 것"에서 나온다. 사전 검색(A)에 해석만 붙여도 viol이 0.75에서 0.17이 된다. 임베딩 없이도 얻는 개선이다.
- 감점 항(λ)의 추가 효과는 작다(C0 λ=0 viol 0.17 → λ=1 0.08).
- 구절 유지: "컴퓨터 아키텍처를 공부하고 싶어요" P@5가 A 0.4, C 0.8.
- 규칙 해석(C)과 LLM 해석(D)은 거의 같다. LLM 형식 실패 2건(JSON 객체 두 개를 이어서 출력)을 제외한 37건에서도 같다(둘 다 0.66).
- 대표 논문 추가(변형 1)는 +0.00~0.04로 유의하지 않다.

## 한계

1. **정답이 순환적이다.** 정답을 프로필 개념으로 정의해서 개념 사전을 쓰는 A에 유리하다. A가 단순 질의에서 1.00인 것은 그 때문이다. 임베딩 방법의 실제 능력은 과소평가됐을 수 있다.
2. **질의를 내가 썼고 규칙 해석기를 같은 질의로 다듬었다.** 규칙(C)이 LLM(D)과 같다는 결과는 학생이 자유롭게 쓴 문장에서도 성립한다는 뜻이 아니다. 독립적인 질의 세트가 필요하다.
3. **사후 분석(A + 해석, 순위 융합)은 같은 39개 질의에서 확인했다.** 설계 선택이 두 가지뿐이고 튜닝하지 않았지만 과대 추정일 수 있다.
4. 질의 39개, 질의당 정답 연구실 1~13개. 작은 차이는 해석하지 않는다.
5. 대표 논문은 앱 교수 60명 중 51개 연구실만 있고, 최근 3개년 논문이 아니다.

## 비용

- Kaggle T4 실행 4.87분(약 0.081시간): 임베딩, Qwen 해석(질의 39개 36초, 질의당 약 0.9초).
- CPU 질의 임베딩: 질의당 약 220ms(Kaggle CPU). 서버에 올릴 수 있는 수준이나 torch 의존성이 생긴다.

# v2: 현재 파이프라인(A) vs 제안 파이프라인(P) 대조 (2026-10-11)

## 설계

- **제안 파이프라인 P**(`pipeline.py`): L0 정규화(동의어) → L1 의도 분기(검색 / 너무 넓음 / 진로 고민 / 범위 밖 / 무의미) → L2 규칙 해석(좋아함·싫어함, 불확실 표시) → L3 사전 검색 + 임베딩 순위 융합(RRF) → L4 확신도 검사. L4가 불확실하다고 보면 라우터(Gemini)를 호출한 것으로 기록하고 끝낸다(결과를 튜닝할 수 없는 구간이라 호출 여부만 평가).
- **라우팅 사유:** 좋아함 없음, 부정 표현이 있는데 싫어함을 못 뽑음, 우선순위·대조 표현, 긴 입력, 사전에도 임베딩에도 안 맞는 구절, 전체 질의의 검색 유사도 낮음.
- **A:** 현재 앱 `ProfileCatalog.search(질의 전체)`.
- **순서(사전 등록):** 개발용 39개(`queries.json`)로 임계값(10퍼센타일)을 정하고 `pipeline.py`·`rule_interpreter.py`를 얼림(`FROZEN_BEFORE_TEST.sha256`) → 시험용 90개(`queries_test.json`, 검색 68 + 비검색 22)를 쓰고 한 번만 실행. 시험용 결과를 본 뒤 코드를 고치지 않았다.
- **성공:** 상위 5개 중 정답 3곳 이상, 다중 관심은 모든 관심에서 최소 1곳, 싫은 주제 혼입 없음. **보정 지표**는 정답 연구실이 1~2곳뿐인 질의(추천시스템 1곳 등)에서 그만큼만 찾으면 성공으로 본다. 사전 지표는 이런 질의에서 누구도 성공할 수 없으므로 결과를 본 뒤 추가한 보정이며, 양쪽에 같이 적용했다.
- **GPU:** Kaggle T4 4.58분(0.076시간, 구절 282개 임베딩). 해석·라우팅·평가는 로컬.

## 결과 (시험용, 검색 질의 68개)

| 지표 | A 현재 앱 | P 제안 |
|---|---|---|
| 성공률 (사전 지표) | 0.51 | 0.62~0.75 (라우팅을 실패~성공으로 가정한 하한~상한) |
| 성공률 (보정 지표) | 0.62 | 0.74~0.87 |
| 조용한 실패(틀렸는데 아무 표시 없음), 보정 | 26/68 | 9/68 |
| 질의별 승패 (보정) | 4 | 17 (47건 동률) |
| 성공률 차이 P−A 95% 구간 (보정) | | +0.07 ~ +0.32 |
| 싫은 주제 혼입 (부정 질의) | 85% | 사전+해석 8%, 제안 23% |
| 라우팅(Gemini 호출) | - | 9/68 = 13% |

유형별 성공률(사전 지표, A → P가 답한 것만): 부정 0.10 → 0.67, 다중 관심 0.62 → 0.88, 다른 표현 0.42 → 0.67, 목적·문제 0.38 → 0.57, 복합 용어 0.88 → 1.00, 단순 0.62 → 0.62, 수업 기반 0.50 → 0.50.

검색이 아닌 질의(22개)에서 A는 결과를 보여주는 오답이 진로 고민 3/6, 범위 밖 4/6, 너무 넓음 1/6. P는 진로 고민 6/6 정답, 너무 넓음 4 정답 + 2 라우팅, 범위 밖 4 정답 + 1 라우팅 + 1 오답("임상 진료랑 환자 치료 연구"), 무의미 3 정답 + 1 라우팅("asdf").

## 해석

- 제안 파이프라인이 모든 지표에서 앞선다. 다만 개발용에서 정한 임계값을 시험용에 그대로 적용한 결과이고, 규칙·사전은 제가 시험용 질의를 쓰기 전에 만들었지만 같은 사람이 설계했다는 한계가 있다.
- 라우팅 신호는 쓸 만했다. 라우팅한 13건 중 우선순위·대조 표현 4건, 중간 정도의 구어 표현(유튜브 추천, 해커 방어 등), 범위 밖·무의미 질의가 포함됐고, 정확히 풀어야 할 질의를 잡았다.
- **임베딩 융합의 효과는 일정하지 않다.** 사전+해석(임베딩 없음)보다 제안이 성공률은 높지만(0.60 → 0.68, 사전 지표) 싫은 주제 혼입은 오히려 높다(8% → 23%). 임베딩이 싫은 주제의 연구실을 끌어올리는 경우가 있다.

## 남은 실패 (시험용 결과를 보고 확인한 것이며 코드는 고치지 않았다)

1. **구절 분리 오류:** 'A이나 B'로 긴 구절을 나눠 의미가 깨진다("AI가 그림이나 사진을 만들어내는 기술" → "AI가 그림", "사진을 만들어내는 기술", "몸에 붙이는 센서로 심박이나 수면을 재는 연구"). 사전 개념에 걸리는 경우가 아니면 쪼개지 말아야 한다.
2. **표현 사전 부족:** "지겹다", "배워봤고" 같은 표현이 부정·우선순위 표지에 없어 라우팅도 안 되고 틀렸다(t21, t34). "너무 어려워서 별로고 암호가"처럼 부정이 이어지면 구절이 오염된다(t25).
3. **조사·서술어 잔여:** "자율주행차 사고를 줄이는 기술"에서 좋아함에 '자율주행'만 남지 않아 사전이 절반만 반응한다.
4. **범위 밖 판정 1건 누락:** 범위 밖 사전에 없는 말("임상 진료")이 임베딩 유사도를 넘어 검색으로 처리됐다.
5. **주제당 정답이 적은 질의**(추천시스템 1곳, 전자기학 등)는 평가 자체가 어렵다.

## 다음 단계

위 1~4를 고친 v3를 만들고, **독립적으로 새로 쓴 질의 세트**(가능하면 설문 자유 서술이나 팀원 작성)로 다시 평가해야 한다. 이번 시험용 질의는 이미 결과를 봤으므로 재사용하지 않는다.
