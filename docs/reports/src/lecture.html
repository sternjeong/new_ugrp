1. 문제 정의: 추천이 아니라 근거 있는 매칭

1.1 검색, 추천, 매칭

검색(search)은 사용자가 쓴 질의에 맞는 문서를 찾는다. 추천(recommendation)은 사용자의 과거 행동으로 선호를 학습한다. 3분커리에는 사용자 행동 로그가 없으므로(콜드스타트) 협업 필터링은 쓸 수 없고, 내용 기반(content-based) 검색이다. 질의는 자연어 한 문장, 문서는 연구실 프로필·과목 설명·논문 초록이다. 게다가 결과에 "왜 이것인가"라는 설명 가능성(explainability)이 요구된다. 이것이 일반 검색과 다른 점이다. 결과 하나하나에 원문 근거가 붙어야 하고, 근거가 없으면 말하지 않아야 한다.

2. 사전 기반 검색과 어휘 불일치

2.1 현재 앱의 엔진

앱의 ProfileCatalog.search()는 개념 사전을 쓴다. concepts.json의 70개 개념 각각에 keywords(과목 본문 매칭용)와 query_keywords(학생 관심 문장 해석용)가 있다. 질의에서 키워드가 나오면 해당 개념이 켜지고, 연구실 프로필의 주요(primary) 주제 중 같은 개념을 가진 연구실에 점수를 준다. 이 점수는 다음 곱으로 만든다.

score(lab) = [ Σc ∈ 일치 개념 specificity(c) + 0.5·(|일치 개념| − 1) ] × grade_weight(lab) × status_weight(lab)

일반적인 개념(기계학습 등)은 낮은 특이성 가중치(specificity)를 받고, 주요 주제가 맞은 뒤에만 보조(secondary) 일반 주제가 0.2씩 더해진다. 개념이 하나도 안 잡히면 질의 낱말이 연구실 요약·라벨·인용에 나오는지 보는 낱말 일치로 후퇴한다. 이 설계는 정밀하다. 사전에 있는 말이면 정확히 그 개념을 가진 연구실을 찾아낸다. E4의 단순 질의에서 현재 앱이 P@5 = 1.00을 낸 이유다.

2.2 어휘 불일치 (vocabulary mismatch)

사전 기반·키워드 기반 검색의 근본 한계는 질의와 문서가 같은 말을 쓰지 않으면 못 찾는다는 것이다. "카메라로 찍은 영상에서 물체를 알아보는 기술"은 컴퓨터비전을 가리키지만 "컴퓨터비전"이라는 낱말은 없다. 정보검색 연구에서 이 문제는 두 갈래로 풀려 왔다.

  • 질의 확장(query expansion): 동의어 사전, 의사 관련성 피드백(pseudo-relevance feedback)으로 질의에 단어를 더한다.
  • 표현 학습: 단어가 아니라 의미 공간의 벡터로 비교한다(3장).

2.3 BM25 짧게 복습

임베딩 이전의 표준은 TF-IDF 계열의 BM25다. 질의 q의 각 낱말 qi에 대해

BM25(q,d) = Σi IDF(qi) · f(qi,d)·(k1+1) / ( f(qi,d) + k1·(1 − b + b·|d|/avgdl) )
IDF(qi) = ln( (N − n(qi) + 0.5) / (n(qi) + 0.5) + 1 )

f는 문서 내 단어 빈도, N은 문서 수, n(qi)는 그 단어를 포함한 문서 수, |d|는 문서 길이, avgdl은 평균 길이, k1·b는 포화·길이 정규화 상수다. 핵심 직관은 (i) 흔한 단어는 가치가 낮고(IDF), (ii) 단어가 많이 나와도 효과는 포화하며, (iii) 긴 문서는 감점한다는 것이다.

한국어의 추가 문제: 교착어

한국어는 조사·어미가 붙어 같은 단어가 "로봇", "로봇은", "로봇이", "로봇을"로 나타난다. 공백 기준 토큰화로는 BM25의 전제(같은 단어는 같은 토큰)가 깨진다. 형태소 분석기나 부분 문자열 일치가 필요하다. 이 프로젝트의 사전은 한국어를 부분 문자열로, 영어를 단어 경계로 매칭한다(concepts.json의 설명). 우리가 질의 해석기를 규칙으로 만들 때도 같은 문제를 겪었다(9장).

2.4 연구자의 눈으로

  • "사전이 있는 말이면 정확하다"는 정밀도(precision) 우위이고 "없는 말은 못 찾는다"는 재현율(recall) 열위다. 두 방식을 섞는 것이 하이브리드 검색(5장)이다.
  • E4에서 정답을 "프로필의 개념 태그"로 정의했기 때문에 사전 검색이 구조적으로 유리했다(7.6절 순환 정답). 평가 설계가 결과를 기울인다는 가장 좋은 사례다.

3. 임베딩 기반 검색

3.1 분포 가설과 이중 인코더

분포 가설(distributional hypothesis): "비슷한 문맥에서 쓰이는 말은 비슷한 뜻이다." 문장 임베딩 모델은 문장을 고정 길이 벡터로 바꿔서, 의미가 비슷하면 벡터가 가깝도록 학습된다. 검색에서는 이중 인코더(bi-encoder) 구조를 쓴다.

s(q,d) = cos( f(q), g(d) ) (우리 실험은 f = g, 정규화 벡터이므로 s = f(q)·f(d))

문서 벡터는 사전에 계산해 저장하고, 질의가 올 때 질의 벡터만 계산해 내적을 구한다. 이것이 크로스 인코더(4장)와의 결정적 차이다. 인덱스 크기를 가늠해 보자. E4의 문서는 873개, 차원은 1024이므로 float32로 873 × 1024 × 4 B ≈ 3.6 MB다. 브루트포스 내적으로 충분하고 근사 최근접 탐색(ANN) 인덱스는 필요 없다.

3.2 대조 학습 (contrastive learning)

이중 인코더는 보통 InfoNCE 손실로 학습한다. 질의 q와 양성 문서 d+, 음성 문서 dj−(배치 내 다른 문서 포함)에 대해

L = − log exp( s(q,d+)/τ ) / ( exp( s(q,d+)/τ ) + Σj exp( s(q,dj−)/τ ) )

τ는 온도다. 양성 쌍을 가깝게, 음성 쌍을 멀게 만든다. 음성 표본을 어떻게 고르는가(hard negative mining)가 성능을 좌우한다. 이 손실에서 중요한 점은 모델이 배우는 것이 "주어진 질의에 어떤 문서가 양성인가"의 통계적 관계이지 논리적 의미가 아니라는 점이다. 이 한계가 9장의 부정 문제로 이어진다.

3.3 bge-m3의 특징

  • BAAI의 다국어 임베딩 모델(BGE M3-Embedding). 100개 이상의 언어, 최대 약 8천 토큰의 긴 입력, 그리고 세 가지 검색 방식(dense 벡터, sparse 어휘 가중치, multi-vector)을 한 모델로 지원한다는 점이 이름의 M3(Multi-lingual, Multi-granularity, Multi-functionality)에 담겨 있다.
  • 우리 실험은 dense 벡터(1024차원)만 쓴다. 한국어 질의와 영어 원문을 같은 공간에서 비교할 수 있어서 선택했다.
  • GPU에서 half 정밀도로 문서를 임베딩하고, 질의 임베딩의 CPU 시간은 약 220 ms였다. 모델 크기(약 5억 6천만 파라미터)에 비해 질의 하나는 짧아서 CPU로도 서비스 가능한 수준이지만, torch 의존성이 생긴다.

3.4 문서 단위와 풀링: 무엇이 "문서"인가

한 연구실을 하나의 벡터로 만들면 여러 주제가 평균으로 뭉개진다. 그래서 우리는 연구실을 여러 개의 짧은 문서(요약 + 주제별 "라벨: 원문 인용")로 쪼갰다. 질의와 연구실의 점수는 문서별 유사도를 풀링해 만든다.

3.5 임베딩의 한계 세 가지 (프로젝트에서 모두 관찰됨)

  1. 부정과 극성: "로봇이 좋아요"와 "로봇이 싫어요"는 같은 단어와 문맥을 공유해 벡터가 가깝다. E4에서 문장 전체 임베딩(B)의 싫은 주제 혼입은 75%로 규칙 사전(A)과 같았다(9장).
  2. 구절 구조: 질의 전체를 하나의 벡터로 쓰면 "컴퓨터 아키텍처"가 "컴퓨터"나 "아키텍처"로 분해되지 않는 대신 다른 단어와 섞여 희석된다. 구절 단위 임베딩이 필요했다.
  3. 짧은 한국어 구어체 질의 ↔ 영어 학술 원문: 영어 인용문에 대한 짧은 한국어 질의는 유사도 절댓값이 낮다. "ㅇㅇ", "asdf", "고양이 사료"의 유사도가 낮다는 점을 이용해 범위 밖을 가려낼 수도 있지만, 반대로 정당한 구어체 질의도 낮게 나올 수 있다. 임계값은 개발용 질의의 10퍼센타일로 정했다(구절 0.529, 질의 0.539).
프로젝트 속 사례: 임베딩 단독은 왜 졌나 (E4, 질의 39개)

전체 P@5가 임베딩 단독 0.47, 사전 0.69였다. 단순 질의에서 임베딩은 0.53이고 사전은 1.00이다. 사전에 있는 말은 사전이 이기는 것이 당연하다. 임베딩이 이기는 질의는 "AI 모델을 작은 기기에서도 빠르게 돌리고 싶어요"(사전 0.2 → 임베딩 계열 1.0), "가상 공간에서 물체를 만지는 느낌"(0.0 → 0.8)처럼 사전에 없는 서술형이었다. 어느 한쪽을 버리는 문제가 아니라 각자가 이기는 영역을 합치는 문제였다.

3.6 연구자의 눈으로

  • 임베딩 공간의 논리적 연산 능력(부정, 양화, 비교)은 열린 문제다. Ettinger(2020)와 Kassner & Schütze(2020)는 사전학습 언어모델이 부정 문장에 둔감함을 보였다. 질의 임베딩이 부정을 인코딩하게 만드는 부정 인지 대조 학습은 작은 연구 질문이 될 수 있다.
  • 교차언어 검색에서 언어 간 유사도의 척도가 다르다(영어-영어 쌍의 유사도가 한국어-영어 쌍보다 높게 나오는 경향). 단일 임계값을 쓰는 우리 방식은 보정(calibration) 대상이다.

4.2 재순위 점수는 보정되지 않는다

재순위 모델의 출력은 원래 로짓이고 우리는 시그모이드로 0~1로 만든다. 그런데 실제 점수 분포는 중앙값 0.002, 90%가 0.05 이하였다. 학습 때 대부분의 쌍이 음성이었으므로 모델이 "아니다"에 확신하는 쪽으로 치우친 것이다. 이 점수는 확률이 아니라 순서 정보만 믿을 수 있는 점수다. 그래서 H1.9(절대 기준점 0.5 컷오프)는 기각됐다. 0.5를 넘는 쌍이 드물어서 컷오프가 사실상 "최소 3개"로만 동작했다.

일반 원리: 점수의 척도 의존성

순위 기반 평가는 점수의 단조 변환에 불변이지만, 임계값 기반 의사결정은 점수 척도에 의존한다. 신경망 점수를 임계값으로 쓰려면 보정(calibration)이 필요하다. 온도 스케일링(temperature scaling), 등온 회귀(isotonic regression) 같은 방법이 있고, 보정 데이터가 없으면 순위나 상대 점수(예: z-점수, 1위와의 격차)를 쓰는 편이 안전하다.

4.4 연구자의 눈으로

  • "점수가 낮은 쌍은 아예 보여 주지 않는다"는 선택적 예측 문제다. 보정된 점수 없이 기권(abstain)을 설계하는 방법은 10장에서 다룬다.
  • 재순위 모델이 우리 도메인(연구실↔과목)에 파인튜닝되지 않았다는 점은 열려 있다. 작은 양의 사람 라벨로 보정이나 경량 파인튜닝을 하면 얼마나 이득인지가 가치 있는 후속 실험이다.

5. 하이브리드 검색과 순위 융합

5.1 왜 섞는가

사전(규칙)은 정밀하고 임베딩은 재현율이 높다. 둘의 오류는 상관이 낮아서 합치면 개선되는 경우가 많다. 합치는 방법은 크게 두 가지다.

(a) 점수 가산 (E1의 방식)

final(lab,course) = emb_score(lab,course) + β · rule_bonus(lab,course)

규칙 가산점은 제목 일치 시 전체(β), 본문에만 일치하면 절반(β/2), 일반 개념(기계학습·통계 등)만 일치하면 β/4를 준다(GENERIC 개념 처리). 문제는 척도 정합이다. 임베딩 점수는 대략 0.3~0.8 범위의 코사인이므로 β = 0.04는 사실상 동점 깨기 수준이고, β = 0.08에서야 순위에 영향을 주기 시작했다. E1 v3에서 β를 0.04에서 0.08로 올린 G·H가 처음으로 v1을 넘은 이유다.

(b) 순위 융합: RRF (E4·E5의 방식)

서로 척도가 다른 두 시스템의 결과는 점수가 아니라 순위로 합치는 편이 간단하다. Reciprocal Rank Fusion(Cormack et al., 2009)은 다음과 같다.

RRF(d) = Σr ∈ 순위 목록들 1 / ( k + rankr(d) )

원 논문은 k = 60을 권하고 우리는 k = 10을 썼다. k가 작을수록 상위 순위의 영향이 크다. 손으로 계산해 보자. 목록 A = (x, y, z, w), B = (y, w, x, v), k = 10이면 y: 1/12 + 1/11 = 0.1742, x: 1/11 + 1/13 = 0.1678, w: 1/14 + 1/12 = 0.1548, z: 0.0769, v: 0.0714로 y, x, w, z, v 순이다. 한 목록에만 나오는 문서(z, v)는 크게 불리하다는 점에 주목하자. 이것이 융합의 보수적 성질이다. 두 시스템이 모두 상위에 둔 항목이 올라간다.

점수 정규화 (z-점수)

구절별 유사도를 연구실 간에 합칠 때 우리는 구절마다 연구실에 대한 유사도를 z-점수로 바꿨다.

z(xi) = ( xi − μ ) / σ (μ, σ: 한 구절의 모든 연구실에 대한 유사도의 평균·표준편차)
score(lab) = meanp ∈ 좋아함 zp(lab) − λ · maxn ∈ 싫어함 max(0, zn(lab))

짧은 구절은 유사도의 전체 수준이 낮고, 긴 구절은 높게 나오는 경향이 있다. z-점수로 구절마다 척도를 맞추면 어떤 구절이 점수를 독점하지 않는다. 싫어함 항은 z > 0(평균보다 가까운 경우)인 연구실만 감점하는 단방향 페널티다.

5.2 프로젝트 속 결과

융합은 언제 이기고 언제 지는가 (E4·E5)

E4(개발 질의): 사전 + 해석 + 임베딩 융합이 P@5 0.84로 사전 0.69, 임베딩+해석 0.66보다 높았다. E5(시험 질의 68개): 융합까지 한 제안 파이프라인이 사전+해석(임베딩 없음)보다 성공률이 높았다(0.74 → 0.81, 보정 지표). 하지만 부정 질의에서 싫은 주제 혼입은 8%에서 23%로 늘었다. 임베딩이 순위를 섞으면서 사전이 의도적으로 뒤로 보낸 연구실을 되살린 것이다. 융합의 이득은 공짜가 아니다. 한 시스템의 제약(여기서는 사전의 싫어함 규칙)이 다른 시스템에 적용되지 않으면 융합이 제약을 깨뜨린다.

5.3 연구자의 눈으로

  • 제약이 있는 융합(constrained fusion): 싫어함 같은 하드 제약은 융합 이후에 적용하거나, 융합 대상 목록 양쪽에 모두 적용해야 한다. 지금 구현은 사전 쪽에만 걸려 있다. 어느 위치에 제약을 두는 것이 이론적으로 최적인지는 단순하고 검증 가능한 질문이다.
  • RRF의 k와 β 같은 하이퍼파라미터를 개발 세트에서 튜닝하고 시험 세트에서 고정해 보고하는 습관이 중요하다(7.5절).

6. 허브니스와 다양성

6.1 허브니스 (hubness)

고차원 공간에서 k-최근접 이웃을 구하면 일부 점이 다른 많은 점의 k-NN 목록에 반복해서 나타나는 현상이 생긴다. 이런 점을 허브(hub)라고 한다. Radovanović et al.(2010)이 "차원의 저주"의 한 측면으로 정리했다. 점 x가 다른 점들의 k-NN에 등장하는 횟수를 Nk(x)라 하면, 차원이 높을수록 Nk의 분포가 오른쪽으로 길게 치우친다(skewness가 커진다). 직관은 이렇다. 고차원에서 거리의 분포는 좁아지고, 데이터 평균(중심)에 가까운 점들이 대부분의 질의에 상대적으로 가깝다.

프로젝트에서의 관찰

E1 v1(방식 A)에서 한 과목이 상위 10개에 든 연구실이 29/56에 달했다. 어떤 연구실에서든 상위에 나오는 "허브 과목"이 있었다는 뜻이다. 내용이 일반적이고 폭넓은 과목(예: 인공지능, 기계학습 개론)이 많은 주제와 평균적으로 가깝기 때문이다.

교정 방법

번역 검색에서 알려진 교정으로 CSLS(Cross-domain Similarity Local Scaling; Conneau et al., 2018)가 있다.

CSLS(x, y) = 2·cos(x, y) − r(x) − r(y)
r(y) = 상위 k개 이웃과의 평균 코사인 (y의 "허브 정도")

우리의 허브 보정은 같은 아이디어로, 과목 평균 유사도에 λ를 곱해 감점했다.

score′(lab, course) = score(lab, course) − λ · meanlab′ score(lab′, course) (v2: λ = 0.7, v3: 0.3, H: 0)

6.2 주제 다양성: MMR

한 연구실의 목록이 한 주제의 과목으로만 채워지면 안 된다는 다양성 요구에는 MMR(Maximal Marginal Relevance; Carbonell & Goldstein, 1998)이 고전적 답이다.

다음 항목 = argmaxd ∉ S [ α · s(q,d) − (1−α) · maxd′ ∈ S sim(d, d′) ]

E1 v2의 D는 이와 비슷하게 같은 주제에서 과목을 하나 더 뽑을 때마다 γ = 0.03을 감점했다.

6.3 왜 교정이 관련도를 떨어뜨렸나

버전허브주제 독점중복관련도0점
A2918280.8840%
C 허브 보정1028320.8245%
D 주제 분산9000.7648%

지표는 의도대로 개선됐는데 정작 관련도는 떨어졌다. 이유를 세 가지로 정리할 수 있다.

  1. 허브가 항상 나쁜 것은 아니다. "인공지능" 과목은 실제로 많은 연구실과 관련이 있다. 모든 연구실에 가깝다는 사실은 결함이 아니라 과목의 속성일 수 있다. 허브 보정은 진짜 관련을 같이 감점한다.
  2. 다양성은 공급이 충분할 때만 의미가 있다. 관련 과목이 3개뿐인 연구실(안성수, 한해욱, 유환조)에 주제 분산을 걸면 관련 없는 과목을 다양성 명목으로 끌어올린다. 문제는 순위가 아니라 목록 길이(수요-공급)였다.
  3. 이 목적 함수는 사람의 만족과 정렬되어 있지 않다. 허브·독점·중복 지표는 "목록이 어떻게 보이는가"를 재고, 관련도는 "맞는가"를 잰다. 서로 다른 목표다(Goodhart의 법칙: 지표가 목표가 되면 좋은 지표가 아니게 된다).
E1 v3의 반전: 단순 하이브리드(H)가 복잡한 보정(G)과 같았다

G(허브 보정 λ=0.3 + 주제당 최소 1개 보장 + β=0.08)와 H(보정·분산 없이 임베딩 + β=0.08)의 관련도가 1.05 대 1.05, 0점 28% 대 28%였다. 오캄의 면도날: 같은 성능이면 더 단순한 H를 택한다. 이 결과는 교정이 쓸모없다는 뜻이 아니라, 우리 데이터 규모와 평가 해상도에서는 효과를 검출하지 못했다는 뜻이다.

6.4 연구자의 눈으로

  • 허브 정도를 질의 분포에 대해 정의하면 문서의 "일반성(generality)"이 된다. 일반성을 따로 모델링해 "일반 과목은 기초로, 전문 과목은 직접 연결로" 분류하면 허브 감점 대신 역할 라벨링이 된다.
  • 수요-공급을 고려한 목록 길이 결정은 "질의별 적정 k 예측"(adaptive-k)이라는 일반적 문제다. 점수 분포의 형태(첫 번째 큰 낙차 지점 등)로 k를 정하는 방법이 있다.

7. 평가 방법론: 정답이 없을 때 어떻게 아는가

이 프로젝트에서 가장 많이 배울 수 있는 부분이다. 정답이 없고 표본이 작으며 평가자도 모델인 상황에서 결론을 내려야 했다.

7.1 검색 평가 지표

P@k와 재현율

P@k = (상위 k개 중 관련 문서 수) / k Recall@k = (상위 k개 중 관련 문서 수) / (전체 관련 문서 수)

nDCG@k

관련도에 등급이 있고 순위가 중요할 때 쓴다.

DCG@k = Σi=1..k reli / log2(i+1) nDCG@k = DCG@k / IDCG@k (IDCG: 이상적인 순서의 DCG)

예: 상위 5개의 관련도(0~2점)가 (2, 2, 0, 1, 0)이라 하자. DCG = 2/1 + 2/1.585 + 0 + 1/2.322 + 0 = 3.693, 이상적 순서 (2,2,1,0,0)의 IDCG = 2 + 1.262 + 0.5 = 3.762이므로 nDCG@5 = 0.982다. 3번째에 0점이 끼어 있어도 상위가 좋으면 점수가 높다. 순위 상단에 가중을 두는 것이 이 지표의 성질이다.

또 한 가지 설계 요소가 채점 재사용이다. 버전이 늘 때마다 모든 쌍을 다시 채점하지 않고, 이전에 채점한 쌍은 그대로 쓰고 새로 나온 쌍만 추가 채점했다(v3: 395쌍 중 새 36쌍, v4: 새 73쌍). 채점자의 기준이 흔들리지 않게 하는 효과도 있지만, 기준이 바뀌면 재사용이 위험해진다(7.4절 E2 v3).

7.3 LLM-as-judge의 위협

LLM을 채점자로 쓰는 방법은 효율적이지만 알려진 편향이 있다(Zheng et al., 2023).

  • 위치 편향: 먼저 제시된 쪽을 선호한다. → 우리는 A/B 순서를 무작위화했다.
  • 자기 선호 편향: 같은 계열 모델의 출력을 높게 평가한다. → 우리 상황에서는 채점자, 질의 작성자, 엔진 설계자가 같은 계열이었다. 가장 큰 구조적 위협이다.
  • 길이·구체성 편향: 긴 문장, 구체적인 문장을 선호한다. E3에서 B(구체적)가 A(모호)보다 구체성에서 압도(1.30 → 3.15)한 것은 부분적으로 이 편향과 구분되지 않는다.
  • 독립성 부재: 한 모델이 5명의 페르소나를 연기하면 5개의 독립 관측이 아니라 한 관측의 변형이다. 실질적 표본 수는 5보다 훨씬 작다.
  • 블라인드의 누수: 문장 형태("이 연구실의 ...와 이어져요")만 보고도 B를 알 수 있다. 우리의 채점 중 추정 매핑은 20건 모두 실제와 일치했다.
평가자 간 일치도 (측정하지 못함)

정석은 둘 이상의 평가자(사람 + 모델)가 같은 항목을 채점하고 일치도를 보고하는 것이다. 두 평가자의 일치도는 Cohen의 κ로 잰다.

κ = ( po − pe ) / ( 1 − pe ) po: 관측된 일치 비율, pe: 우연에 의한 기대 일치 비율

우리는 평가자가 하나였으므로 κ를 낼 수 없었다. "채점은 상대 비교로만 쓴다"는 표현은 이 한계를 인정한 것이다. 논문이나 심사에서는 이 부분이 곧바로 지적된다.

7.4 기준이 바뀌면 비교할 수 없다 (E2 사례)

E2 v3의 채점은 "직접 적용된다·필수적이다·핵심이다" 같은 근거에 없는 연결 주장을 문장의 과목 내용이 맞아도 faithful 0으로 매겼다. v2에서는 이를 정확으로 봤다. 그래서 같은 M4b가 v2에서 정확도 0.73, v3에서 0.27이 됐다. 시스템이 바뀐 것이 아니라 자(尺)가 바뀐 것이다. 우리는 표 안에서만 비교하고 버전 간 비교를 하지 않았다. 일반 원칙: 실험 간 수치를 비교하려면 평가 프로토콜을 고정해야 한다. 프로토콜을 바꿨다면 새 기준으로 이전 조건을 다시 채점해야 한다.

7.5 개발/시험 분리와 사전 등록

E5에서 취한 절차는 다음과 같다.

  1. 개발용 질의 39개로 임계값(구절 0.529, 질의 0.539)을 정한다.
  2. 파이프라인 코드를 얼리고 해시를 기록한다(FROZEN_BEFORE_TEST.sha256).
  3. 독립 시험용 질의 90개를 쓰고 한 번만 실행한다.
  4. 시험 결과를 본 뒤 코드를 고치지 않는다. 실패 원인은 "남은 문제"로만 기록한다.

이는 데이터에 의한 과적합(overfitting to the test set)을 막는 최소 절차다. 시험 세트를 보고 파이프라인을 고치면 시험 세트는 더 이상 시험 세트가 아니다. 또한 어떤 결정을 결과를 보기 전에 기록해 두면 사후 합리화(HARKing, Hypothesizing After the Results are Known)를 피할 수 있다.

우리가 한 사후 변경: 보정 지표

사전 지표는 "성공 = 상위 5개 중 3곳 이상 정답"이었다. 시험을 돌려 보니 정답이 1~2곳뿐인 주제(추천시스템 1곳 등)에서는 이 조건이 수학적으로 불가능했다. 그래서 "정답 수가 부족하면 그만큼만 찾아도 성공"으로 결과를 본 뒤 보정했다. 현재와 제안 양쪽에 똑같이 적용했고 사전 지표 결과도 함께 보고했다. 결론의 방향은 둘 다 같았다(0.51 vs 0.62~0.75, 0.62 vs 0.74~0.87). 이처럼 사후 변경은 숨기지 않고 두 수치를 같이 적는 것이 정직한 방식이다.

7.6 순환 정답

E4·E5의 정답은 "연구실 프로필에서 해당 개념을 가진 연구실"이었다. 이 개념 체계는 현재 앱의 사전과 같다. 그래서 단순 질의에서 현재 앱이 1.00을 낸 것은 당연한 결과다. 평가 기준이 한 시스템의 내부 표현과 같으면 그 시스템에 유리하다. 이런 편향을 줄이려면 (i) 정답을 시스템과 독립된 사람이 지정하거나, (ii) 사람이 질의별로 상위 결과의 적합성을 직접 판정하는 pooling 평가를 한다. 이번 실험은 (i)이 부족했고 이 한계를 보고서에 명시했다.

7.7 통계적 불확실성: 질의 단위 부트스트랩과 부호 검정

E5에서 두 시스템의 성공률 차이(제안 − 현재)의 95% 구간을 질의 단위 부트스트랩으로 구했다.

for b in 1..B (B = 3000):
    idx = 질의 n개를 복원 추출
    diff_b = mean( success_P[idx] − success_A[idx] )
구간 = diff의 2.5, 97.5 퍼센타일 → 보정 지표 +0.07 ~ +0.32

질의가 무작위 표본이라는 가정이 핵심이다. 우리 질의 세트는 유형별로 계층적으로 구성했으므로 유형별 비율은 임의가 아니다. 또 같은 질의에서 두 시스템을 비교하므로 짝지은(paired) 비교가 맞다. 질의별로 P가 이긴 건수와 A가 이긴 건수만 보는 부호 검정(sign test)도 가능하다. 보정 지표에서 P가 이긴 질의 17, A가 이긴 질의 4, 동률 47이었다. 동률을 빼고 n = 21, 귀무가설 하에서 이길 확률 0.5라면

p = 2 · Σk=17..21 C(21,k) / 221 = 2 · 7547 / 2097152 ≈ 0.007

사전 지표에서는 15 대 4(n = 19)로 p ≈ 0.019다. 둘 다 유의하지만, 이 p값은 "질의가 모집단에서 임의 표본"이라는 가정에 의존하고, 이 가정은 위 위협들(작성자 동일, 순환 정답) 때문에 약하다. 통계적 유의성은 타당성을 보증하지 않는다.

7.8 연구자의 눈으로

  • "평가 프로토콜의 타당성(validity)"을 논문 한 절로 쓸 수 있는 수준으로 분석하는 연습이다. construct validity(재려는 것을 재는가), internal validity(결과가 교란 없이 원인에 기인하는가), external validity(다른 질의·연구실로 일반화되는가)로 나눠 우리 실험을 점검해 보자.
  • 작은 데이터에서 평가자 일치도를 높이는 방법: 채점 기준 문서(rubric), 예시 보정(calibration set), 불일치 항목에 대한 합의 세션.

8. LLM 생성, 환각, 그리고 사실성 검사

8.1 환각이란

환각(hallucination)은 모델이 입력(근거)이나 사실에 없는 내용을 그럴듯하게 생성하는 것이다. 요약·생성 연구에서는 내재적(intrinsic) 환각(근거와 모순)과 외재적(extrinsic) 환각(근거로 검증 불가)으로 나눈다(Maynez et al., 2020; Ji et al., 2023). 우리가 본 것은 대부분 외재적이다. 예를 들어 "시뮬레이션 기법이 포논 연구의 중요한 도구"는 근거 문장에 그런 말이 없다. 문장 속 과목 내용은 맞는데 연결 주장이 지어낸 것이다.

8.2 E2의 핵심 발견: 환각은 연결에서 나온다

v1에서 로컬 LLM(M4)은 가장 자연스럽고 도움이 되는 문장을 썼지만 27%가 근거에 없는 내용이었다. 단어 비교(M5)와 재순위 일치도(M6)로 걸러 보려 했고, 프롬프트를 개선(M4b)해도 줄지 않았다. 환각의 구조를 분석하니 문장은 두 부분으로 이뤄져 있었다.

부분내용환각 위험
사실 부분"이 과목에서 PID 제어를 배워요" — 근거 문장에서 추출 가능낮음 (번역 오류 제외)
연결 부분"그래서 이 연구실의 연구에 직접 적용된다" — 근거에 없는 주장높음

그래서 v3에서는 역할을 나눴다. 연결 부분은 고정 템플릿("이 연구실의 '{주제}' 연구와 이어져요")이 쓰고, LLM은 과목이 가르치는 내용을 한국어 명사구로 옮기는 일만 한다. LLM이 쓸 수 있는 공간이 줄어드니 환각이 줄어든다.

구조적 해법: 생성 공간 제약

M4b 부정확 44/60 → M7 4/60. 같은 LLM을 써도 무엇을 생성하게 하는가로 신뢰성이 달라졌다. 일반 원리: 신뢰성이 중요한 곳에서는 LLM에게 "자유 서술"이 아니라 "구조화된 작은 과제"(슬롯 채우기, 추출, 분류)를 맡기고, 서술은 결정적 코드가 조립한다. 이는 constrained decoding, 구조화 출력, 도구 사용(tool use) 계열 설계와 같은 맥락이다.

8.3 NLI 기반 사실성 검사

자연어 추론(NLI)은 전제(premise)와 가설(hypothesis)의 관계를 함의(entailment)·중립(neutral)·모순(contradiction)으로 분류한다. 요약의 사실성 검사에 NLI를 쓰는 접근은 널리 쓰인다. 우리 구성은 이렇다.

전제 = 과목 근거 문장, 가설 = "이 수업은 {LLM이 만든 명사구}를 다룬다"
통과 조건: P(entailment | 전제, 가설) ≥ 0.5 (NLI_MIN) → 실패하면 M2(영어 근거 인용)로 대체

모델은 다국어 NLI(mDeBERTa-v3-base를 XNLI와 다국어 NLI 데이터로 학습한 공개 모델)다. 영어 근거와 한국어 명사구를 교차언어로 판정할 수 있어서 선택했다. v2의 단어 비교 검사는 "영어 근거 문장을 한국어로 환언한 정상 문장"도 "근거 밖 단어"로 오판해 63~83%를 대체했다. NLI는 의미 수준에서 판단하므로 대체율이 27%로 줄었다. 그러나 부정확 4건 중 2건만 걸렀다. NLI 모델도 번역 오류("carrier" → "매개체")를 잡지 못하는 경우가 있다. 번역된 의미가 영어 원문과 반드시 모순되지는 않기 때문이다.

8.5 양자화와 디코딩 (구현 메모)

  • 4비트 양자화(nf4): Qwen2.5-7B-Instruct를 bitsandbytes로 4비트(NormalFloat4)로 올려 T4(16GB)에 약 6GB로 적재했다(Dettmers et al., 2023, QLoRA의 NF4). 정밀도 손실이 있지만 추출·번역 같은 작은 과제에는 충분했다.
  • 결정적 디코딩: do_sample=False (그리디). 평가를 재현 가능하게 하려면 샘플링을 끄고 시드를 고정한다.
  • 출력 정리: 한자·깨진 토큰("_technologies") 제거, 첫 줄만 취함, 조사 처리 함수 josa()("을/를" 선택, 받침 유무 판별). 조사가 틀린 문장("을(를)")은 신뢰감을 크게 깎는다.

8.6 연구자의 눈으로

  • "근거를 인용하는 설명 생성"의 평가 지표 설계: faithfulness(근거에 의해 뒷받침되는가), informativeness(구체적인가), attributability(어느 근거 문장 때문인지 명시했는가). 우리는 faithful 0/1, specific·fluent·useful 1~3으로 단순하게 잡았다.
  • 사실성과 정보성의 트레이드오프: 구체적일수록 틀릴 위험이 커진다. E3에서 B가 구체성 1.30 → 3.15를 얻은 대가로 정확성이 3.75 → 3.10으로 떨어졌다. 두 목표를 동시에 최적화하는 파레토 곡선을 그리는 실험이 가능하다.

9. 질의 이해: 부정, 구절, 의도

9.1 왜 임베딩은 부정에 약한가

대조 학습(3.2절)이 가르치는 것은 "이 질의에 이 문서가 맞는가"의 통계적 관계다. "로봇이 싫다"와 "로봇이 좋다"는 거의 같은 단어와 같은 문맥에서 쓰이므로 벡터가 가깝다. 모델이 "싫다"의 극성을 질의 벡터의 방향으로 반영하기보다 "로봇이라는 주제"에 압도적으로 반응한다. 그래서 E4에서 문장 전체 임베딩(B)은 싫은 주제의 혼입이 75%였다. 이는 규칙 사전(A)과 같은 수치다. 두 방법이 서로 다른 이유로 같은 실패를 한 것이다. 사전은 "싫어"를 모르고, 임베딩은 극성이 약하다.

해법은 부정 처리를 모델 밖으로 빼서 명시적으로 다루는 것이다. 질의를 먼저 구조화(좋아함 / 싫어함)하고, 좋아함 구절로 검색한 다음, 싫어함 구절과 가까운 후보를 후단에서 감점한다.

결과 (E4, 부정 질의 12개)

싫은 주제가 상위 5개에 섞인 질의 비율: 현재 앱 75%, 문장 임베딩 75%, 규칙 해석 + 임베딩 8%, 사전 + 해석 17%. 임베딩 없이 싫은 구절을 질의에서 제거하는 것만으로 대부분의 효과가 나왔다. 감점 항(λ)의 추가 이득은 17% → 8%로 작았다.

9.2 규칙 파서의 설계 (한국어)

rule_interpreter.py는 세 가지 규칙으로 동작한다.

  1. "A보다(는) B", "A 말고 B": 앞이 싫어함, 뒤가 좋아함.
  2. "싫(은데|고)", "별로(고)", "관심 없(고)", "질렸(고)", "빼고" 앞의 구절을 싫어함으로 떼어 냄.
  3. 남은 문장에서 서술 어미("하고 싶어요", "궁금해요", "좋아요" 등)를 지우고, "과·와·랑·이랑·이나·나"로 구절을 나눔. 구절 안의 공백은 유지.

교착어의 구조 때문에 정규식 규칙이 쉽게 깨진다. E5 시험에서 관찰된 실패를 보자.

입력해석 결과문제
AI가 그림이나 사진을 만들어내는 기술["AI가 그림", "사진을 만들어내는 기술"]"이나"는 병렬 접속이지만, 서술어 "만들어내는"이 두 명사를 모두 지배한다(접속의 범위 모호성, coordination scope). 규칙이 "이나"에서 쪼개 서술어를 한쪽에만 붙였다
양자는 너무 어려워서 별로고 암호가 재밌어요싫어함 ["양자는 너무"], 좋아함 ["별로고 암호"]"어려워서"와 "별로고"가 이어진 복합 이유절. 규칙의 경계가 하나만 처리
AI는 이제 지겹고 하드웨어 설계가 끌려요좋아함 ["AI는 이제 지겹고 하드웨어 설계"]"지겹다"가 부정 표지 사전에 없음. 라우팅 신호도 안 걸려 조용한 실패
무선통신은 이미 배워봤고 이번엔 보안을 해보고 싶어요좋아함 ["무선통신은 배워봤고 보안"]"배워봤고"가 우선순위 표지에 없음. 의미는 "무선통신은 덜 원함"

이 오류들은 두 종류로 나뉜다. (i) 어휘 누락(지겹다, 배워봤다)은 사전 확장으로 해결되고, (ii) 구조 모호성(접속의 범위)은 규칙으로 완전히 해결하기 어렵다. (ii)는 구문 분석(dependency parsing)이나 LLM 같은 언어 이해가 필요하다. 이것이 규칙이 풀 수 없는 영역을 LLM 라우터에 넘기는 설계의 이론적 근거다.

해법 아이디어: 사전 우선 구절 분할 (longest-match)

구절을 쪼개기 전에 개념 사전과 동의어 사전에서 가장 긴 일치(longest match)를 먼저 찾아 보호한다. "컴퓨터 아키텍처"는 한 덩어리로 보호되고, 사전에 없는 서술형 구절은 접속 분할을 하지 않는다(쪼개기 대신 문장 전체를 구절 하나로 둠). 이 휴리스틱은 사전에 있는 용어에서는 정밀하고, 없는 서술형 질의에서는 임베딩이 문장 전체로 처리하므로 쪼개짐의 피해를 피한다.

9.3 의도 분류

모든 입력이 연구실 검색 요청은 아니다. E5에서 다섯 가지 의도를 구분했다.

의도예처리 방식
검색"강화학습에 관심 있어요"L2~L3 검색 실행
너무 넓음"컴퓨터가 좋아요", "AI"검색하지 않고 세부 주제를 되묻기
진로 고민"대학원 갈지 모르겠어요", "교수님께 메일을 어떻게 써요"다른 안내(연구실 검색이 아님)
범위 밖"유기화학 합성 연구실", "경제학이랑 데이터"데이터 범위(현재 4개 학과) 안내

E5의 비검색 질의 22개에서 현재 앱은 진로 고민 6개 중 3개, 범위 밖 6개 중 4개에서 엉뚱한 연구실 목록을 보여 줬다. 제안 파이프라인은 진로 고민을 6/6 맞혔다. 의도 분기는 "아무 결과나 보여주기"가 "잘 모르겠다고 말하기"보다 항상 나쁘다는 원칙에서 출발한다.

9.4 연구자의 눈으로

  • 부정 인지 검색(negation-aware retrieval): 질의 임베딩 단계에서 극성을 반영하는 모델은 열린 문제다. 우리 방식은 "질의 분해 + 후단 감점"이라는 모듈형 해법이고, 이를 end-to-end 학습으로 대체하면 어떤 이득이 있는지가 연구 질문이다.
  • 한국어 접속의 범위 모호성과 부정 범위(negation scope) 해결을 위한 소규모 평가 세트를 만드는 것만으로도 작은 기여가 될 수 있다.

10. 불확실성과 라우팅: 선택적 예측

10.1 문제: 모를 때 모른다고 하기

모든 질의에 답하는 시스템은 틀린 답도 같은 자신감으로 보여 준다. 사용자가 받는 피해는 틀린 답 자체보다 틀렸다는 표시가 없다는 데 있다. E5에서 이를 "조용한 실패(silent failure)"라 정의했다: 틀렸는데 되묻기·라우팅 같은 표시가 없는 질의. 이는 선택적 분류(selective classification) 또는 reject option 문제와 같다(Chow, 1970; El-Yaniv & Wiener, 2010; Geifman & El-Yaniv, 2017).

10.2 위험-범위 (risk–coverage) 곡선

예측기 h와 선택 함수 g(x) ∈ {0, 1}(1이면 답한다)에 대해

coverage = P( g(x) = 1 ) selective risk = E[ ℓ(h(x), y) · g(x) ] / coverage

기권(abstain)을 늘리면 범위(coverage)가 줄고 위험(risk)도 줄어든다. 좋은 선택 함수는 같은 coverage에서 risk가 더 낮다. 우리 결과(보정 지표, 검색 질의 68개)를 이 틀에 놓아 보자.

범위 (답한 비율)답한 것의 위험 (틀린 비율)
A 현재 앱 (기권 없음)68/68 = 100%26/68 = 38%
제안 (라우팅 포함)59/68 = 87%9/59 = 15%

범위를 13% 포기하고 위험을 38%에서 15%로 낮췄다. 단, 라우팅된 9개 질의는 Gemini가 처리하므로 실제 시스템의 정확도는 그 결과에 달려 있다(우리는 호출 사실만 기록했다). 라우터의 가치는 기권 신호가 오류를 얼마나 선택적으로 포착하는가(낮은 coverage 손실로 높은 risk 감소)로 평가한다.

10.3 기권 신호 설계

보정된 확률 없이 기권 신호를 만들어야 했다. 일반적인 선택지에는 소프트맥스 최대 확률(MSP; Hendrycks & Gimpel, 2017)이 있지만, 우리는 확률 분류기가 없다. 그래서 구조적 신호와 점수 신호를 조합했다.

신호의미감지 방법
no_likes파서가 좋아함을 못 찾음구조적: 해석 결과가 비었는가
neg_cue_unparsed부정 표현이 있는데 싫어함을 못 뽑음구조적: 부정 표지 정규식 ∧ 싫어함 빈 목록
priority대조·망설임 표현("~도 좋지만", "더 끌려요")구조적: 정규식. 규칙이 무게를 알 수 없는 문장
long_input70자 초과구조적: 복합 문장은 규칙 파서의 신뢰도 하락
unmatched_phrase어떤 좋아함 구절이 사전에도 없고 임베딩 최대 유사도도 임계 미만점수: 구절 유사도 < 0.529
weak_query사전 결과가 없고 질의 전체의 유사도가 낮음점수: 질의 유사도 < 0.539

구조적 신호는 해석기가 자기 한계를 아는 지점이다. 이런 신호는 보정이 필요 없고 이유를 설명할 수 있다. 점수 신호는 임계값이 필요하며 개발용 질의의 10퍼센타일로 정했다. 임계값의 의미는 "범위 안 질의의 하위 10%만 오기권으로 허용하겠다"는 정책이다. 임계값을 낮추면 기권이 줄고 위험이 늘어난다(곡선의 점 이동).

10.4 캐스케이드와 라우터

저렴한 모델로 먼저 시도하고 불확실할 때만 비싼 모델을 부르는 설계를 캐스케이드(cascade)라 한다. LLM API 비용을 줄이는 FrugalGPT(Chen, Zaharia, Zou, 2023)가 대표적 연구다. 우리 구조에서는 규칙·사전·임베딩이 1단계이고 Gemini가 2단계(라우터)다. 라우터에 요구되는 조건을 정리하면 다음과 같다.

  1. 해석만 맡긴다: 출력은 구조화 JSON {좋아함, 싫어함, 의도, 되묻기}으로 한정. 검색·추천은 결정적 코드(L3)가 한다. (8장의 교훈)
  2. 출력 검증: 구절이 원문의 부분 문자열이거나 사전 동의어여야 하고, 싫어함이 좋아함에 섞이면 폐기한다.
  3. 후퇴(fallback): 타임아웃·형식 오류 시 규칙 결과를 쓴다. 같은 정규화 질의는 캐시한다.
  4. 호출 비율 모니터링: E5 시험에서 13%. 이 값이 서비스 비용·지연의 상한이므로 목표로 관리한다.
E5의 한계: 라우팅 신호가 놓친 것

조용한 실패 9건 중 상당수는 신호를 하나도 못 켰다. "지겹다", "배워봤고" 같은 어휘 누락과 구절 분리 오류다. 이런 오류는 구조적 신호만으로는 감지할 수 없다. 감지하려면 (i) 사전 확장으로 신호 커버리지를 늘리거나, (ii) 해석 결과에 대한 독립적 검증(예: 구절 재조합이 원문을 복원하는가, 구절당 사전 일치 개수)을 추가하거나, (iii) 해석이 맞았는지 사용자에게 칩으로 보여주고 수정받는 인터페이스 안전장치가 필요하다.

10.5 연구자의 눈으로

  • 라우팅 신호의 정밀도·재현율을 정의해 보자. 신호가 켜진 질의 중 "라우팅 없이 답했다면 틀렸을" 비율(정밀도), 틀린 질의 중 신호가 켜진 비율(재현율). 우리는 이를 측정하지 않았다(연습문제 8).
  • 외부 LLM 호출 비용 c와 오답 비용 e가 있을 때 최적 임계값은 (오답 확률) × e = c의 지점이다. 이를 비용 민감 의사결정(cost-sensitive decision)으로 형식화할 수 있다.

11. 시스템 설계: 무엇을 언제 계산하는가

11.1 오프라인 vs 온라인 분해

입력이 무엇에 의존하는가로 계산 시점이 결정된다.

11.2 지연 예산

대화형 검색의 응답을 1초 안에 맞추는 것을 목표로 잡으면 대략 이렇게 쓴다: 규칙 해석 + 사전 검색 수십 ms, 질의 임베딩 약 220 ms(CPU), 내적·융합 수 ms, 라우터는 호출될 때만(수백 ms~수 초). 라우터를 hot path에 두지 않고 "해석 중" 표시나 비동기 갱신으로 처리하는 UX 결정이 필요하다.

11.3 재현성

  • 동결: 시험 전에 코드 해시를 기록했다. 결과 파일, 설정(시드, 임계값, 모델 ID), 실행 로그를 폴더에 보존했다.
  • 입력 선언: 노트북 메타데이터의 gpuhub.inputs에 필요한 파일을 선언한다. 입력이 암묵적이면 재현할 수 없다.
  • 결정적 설정: 그리디 디코딩, 고정 시드, 같은 정규화·전처리 규칙.

12. 미구현 영역: 연구 가이드 설계

12.1 왜 자유 생성이 위험한가

가이드는 "이 연구실에서 지금 시작할 탐색"과 "추가 준비"를 제안한다. 위험은 실제로 진행 중이지 않은 프로젝트를 있는 것처럼 말하는 것이다. 검색 증강 생성(RAG)은 검색된 문서를 LLM의 컨텍스트에 넣어 생성하게 하지만, 생성 단계에서는 여전히 연결·추론의 환각이 가능하다. 우리 E2의 교훈은 RAG의 "생성"을 그대로 쓰지 말라는 것이다.

     {문제, 대상·데이터, 방법, 결과, 필요한 지식(추론 표시), 원문 구절 오프셋}

import numpy as np

def cosine_maxsim(Q, D, owner):          # Q: (m,d) 구절 임베딩, D: (n,d) 문서 임베딩, owner: 문서 → 연구실 인덱스
    S = Q @ D.T                          # 정규화 벡터면 내적 = 코사인
    return np.stack([S[:, owner == l].max(axis=1) for l in range(owner.max()+1)], axis=1)

def zscore(x):  return (x - x.mean()) / (x.std() + 1e-9)

def rrf(*rank_lists, k=10):
    s = {}
    for L in rank_lists:
        for i, d in enumerate(L):
            s[d] = s.get(d, 0) + 1 / (k + i + 1)
    return [d for d, _ in sorted(s.items(), key=lambda t: -t[1])]

def ndcg_at_k(rels, k=5):
    dcg  = lambda r: sum(x / np.log2(i + 2) for i, x in enumerate(r[:k]))
    return dcg(rels) / dcg(sorted(rels, reverse=True))

def bootstrap_ci(diffs, B=3000, seed=0):  # diffs: 질의별 (P 성공 − A 성공)
    rng = np.random.default_rng(seed)
    means = [rng.choice(diffs, len(diffs)).mean() for _ in range(B)]
    return np.percentile(means, [2.5, 97.5])
