# 추천 근거 설명과 연관 과목 선정 논의 정리

- 작성일: 2026-10-08
- 범위: 연구실 목록의 "어떤 내용을 보고 연결했나요?" 답변과 연구실 상세 화면("배운 것에서, 시작해 볼까요?")의 연관 과목 선정 방식.
- 상태: **논의와 제안 단계.** 코드와 데이터는 바꾸지 않았다. 아래의 "방향"은 논의에서 합의된 흐름이며 구현 승인이 아니다. 구현을 시작하면 `docs/analysis/SERVICE_CODEBASE_ANALYSIS.md`와 `docs/product/PRODUCT_PLAN.md`에 반영한다.

## 1. 핵심 요약

1. 현재 추천 이유는 `라벨 + "관련 내용을 연구실 자료에서 확인했습니다."` 형식의 고정 문장과 영어 원문 인용뿐이다. 사용자의 어떤 말이 왜 연결됐는지 알 수 없다.
2. 현재 엔진은 단어가 있는지만 보고 뜻은 보지 않는다. 그래서 **"나는 로봇을 싫어해요"를 입력해도 로봇 연구실 7곳을 추천한다.** 이 문제를 해결하기 전에는 근거 설명을 보강해도 틀린 이해를 근거처럼 보여주게 된다.
3. 연관 과목 매칭에 필요한 데이터는 거의 충분하다. 병목은 데이터 양이 아니라 70개 단어 목록 기반의 매칭 방식이다.

## 2. 확인된 사실 (2026-10-08 실제 실행·집계)

### 부정 표현 처리 실패

| 입력 | 현재 결과 |
|---|---|
| 나는 로봇을 싫어해요 | 로봇 연구실 7곳 추천 |
| 로봇 말고 반도체가 궁금해요 | 로봇 연구실이 상위에 섞임. "말고"의 "말"이 음성처리 개념으로 잡힘 |
| 로봇은 별로고 자연어처리에 관심 있어요 | 1위가 로봇+자연어처리 연구실 |

### 근거 설명의 모호함

- 예: "비전 기반 로봇 조작 관련 내용을 연구실 자료에서 확인했습니다." + 영어 원문 1~2개
- 빠진 것: 사용자가 쓴 말, 연결 방식(연구 대상인지 도구인지), 근거 출처의 강도, 연결되지 않은 관심

### 연관 과목 선정의 문제

- 연구실 핵심 주제와 과목 개념 태그가 하나라도 겹치면 후보에 넣는다. 정렬은 (제목 일치 2점, 본문 일치 1점) 합계 → 과목 코드 순이다.
- 로봇 질의 1위 연구실에서 일반 AI 과목 4개가 상위를 차지하고 **로보틱스개론이 10개 중 맨 마지막**이었다.
- 본문의 "선수과목: …인공지능" 문구 때문에 지능형 반도체 소자가 연관 과목에 들어왔다.
- 과목별 이유 문장이 "AI·기계학습 지식을 연결해볼 수 있습니다."로 반복된다.
- 사용자가 어떤 관심으로 연구실에 들어왔는지와 무관하게 같은 과목 목록을 보여준다.

### 데이터 충분성

| 데이터 | 상태 |
|---|---|
| 과목 설명 | 419개 중 418개 (중앙값 약 160자) |
| 학습 목표 | 408개 (중앙값 약 330자) |
| 주차별 강의 계획 | 397개 (중앙값 약 500자) |
| 선수과목 | 336개 |
| 과목 수준 | 100~400번대 학부 과목만 있음. 대학원 과목 없음 |
| 개념 태그가 하나도 없는 과목 | 110개 (내용은 있으나 70개 어휘에 없어 연결 실패) |
| 연구실 원문 | 수집 60건 기준 중앙값 약 8,000자. 500자 미만은 5건 |
| 매칭에 쓰는 연구실 인용 | 중앙값 73자. 원문 대부분을 활용하지 않음 |
| 자료가 얕거나 없는 연구실 | thin 5곳, insufficient 2곳 |

데이터에 없는 정보: "이 연구실에서 실제로 도움이 되는 과목". 이 정보는 선배와 후기에서 따로 받아야 한다.

## 3. 방향 (논의에서 합의, 구현 미승인)

### 3-1. 입력 이해 단계 추가 (최우선)

검색할 때 Claude Haiku 4.5를 한 번 호출해 입력 문장을 구조화한다. 점수 계산은 기존 규칙 엔진이 계속 맡는다.

```
입력: "로봇 말고 반도체가 궁금해요"
→ { "좋아함": [{"주제": "반도체 소자", "근거 문구": "반도체가 궁금해요"}],
    "싫어함": [{"주제": "로봇", "근거 문구": "로봇 말고"}] }
→ 규칙 엔진: 반도체 연구실 추천, 로봇이 핵심 주제인 연구실은 제외하거나 아래로 내림
```

안전장치:
1. 주제는 기존 개념 어휘(`concepts.json`, 70개) 안에서만 고른다. 목록에 없는 주제는 버린다.
2. "근거 문구"가 사용자 입력에 실제로 있는 글자인지 코드로 확인한다. 없으면 버린다.
3. API 호출이 실패하면 기존 키워드 방식으로 돌아간다. 이때 "싫어, 별로, 말고, 빼고, 관심 없" 같은 부정 표현 근처의 단어는 제외하는 규칙을 적용한다.
4. 결과 위에 "이렇게 이해했어요: 👍 반도체 소자 👎 로봇 [수정하기]"를 보여주고 사용자가 고칠 수 있게 한다.

이 방식의 부수 효과: 어휘 목록에 없는 표현도 기존 개념으로 연결할 수 있다(예: "자율주행차가 길을 찾는 원리" → 로봇·경로계획).

### 3-2. "어떤 내용을 보고 연결했나요?" 답변 구조

```
내가 쓴 말:    "반도체가 궁금해요"
연결된 주제:   반도체 소자 (연구 대상)
연구실 자료:   한국어 한 줄 풀이 + 원문 링크 + 출처(연구실 소개글 / 논문 제목 / 연구실 이름)
찾지 못한 것:  입력한 관심 중 이 연구실 자료에 없는 것
제외한 것:     사용자가 싫다고 한 주제
```

| 단계 | 기술 | 위치 |
|---|---|---|
| 입력 이해 | Claude Haiku 4.5, 검색마다 1회 호출 + 검증 코드 | `profile_catalog.py`의 `search()` 앞단 |
| 연결 문장 | 역할(domain/method)별 Python 문자열 템플릿 | `profile_catalog.py`의 `search()` |
| 인용 한국어 풀이 | Claude API로 미리 일괄 생성(`quote_ko`)하고 사람이 검토 | 새 `tools/build_quote_ko.py`, `lab_profiles.jsonl`, 기존 검토 페이지 |
| 화면 | 순수 JS + CSS, 키워드 강조 | `app.js`의 `labCard`, `styles.css` |
| API 응답 | 새 필드 `explanation` 하나 추가 | `/api/search` |
| 테스트 | 기존 `unittest` | `tests/test_profile_catalog.py` |

서버·DB·프런트엔드 구조는 바꾸지 않는다(Python 표준 라이브러리 서버, 순수 JS, JSON 데이터 파일).

### 3-3. 연관 과목 선정

1. **점수:** 공유 개념마다 `연구실 쪽 가중치 × 과목 쪽 강도 × 사용자 관심 가산`을 계산해 더한다.
   - 연구실 쪽: 핵심 주제는 1, 일반 개념은 기존 `SPECIFICITY` 값 적용
   - 과목 쪽: 제목 3 > 학습 목표·강의 계획 2 > 설명 본문 1. 선수과목 문구에서만 일치하면 0
   - 사용자 쪽: 사용자가 이 연구실로 들어온 주제이면 ×1.5
2. **제외:** 일반 개념(AI 등) 하나만 겹치는 과목은 뺀다. 단, 연구실 주제가 ML 자체인 경우는 예외로 둔다. 비슷한 과목(인공지능 / 인공지능기초 / 기계인공지능)은 하나로 묶고 나머지는 접는다.
3. **묶어서 보여주기:** 기초(100~200번대이거나 다른 추천 과목의 선수과목) / 핵심(연구실의 구체 주제가 제목에 들어간 과목) / 심화(400번대). 화면에는 6~12개를 목표로 한다.
4. **과목별 이유:** 연구실 주제와 과목 근거를 함께 쓴다. 예: "이 연구실의 비전 기반 로봇 조작 연구에 필요한 로봇 운동학을 다뤄요."
5. **사람의 판단:** 검토 도구에 연구실별 과목 고정/제외 필드를 추가한다. 후기와 선배 프로필에서 "도움이 된 과목"을 받아 가장 강한 근거로 쓴다.
6. **매칭 범위 확장:** 개념 어휘를 넓히거나, 연구실 원문 전체와 과목 강의 계획을 매칭에 활용해 태그 없는 과목 110개를 줄인다.

## 4. 기각·수정된 안

| 기각·수정된 안 | 이유 |
|---|---|
| 단순 키워드 추출만으로 "내가 쓴 말"을 보여주는 방식 | 부정 표현을 구분하지 못한다. "로봇을 싫어해요"를 로봇 관심으로 보여주면 틀린 이해를 근거처럼 제시하게 된다. |
| "검색할 때는 AI를 부르지 않는다"는 원칙 | 위 문제 때문에 수정했다. 검색마다 짧은 AI 호출 1회를 허용하되, 실패하면 규칙 방식으로 돌아간다. |
| 과목 매칭 개선을 위해 데이터 수집을 먼저 하는 방향 | 과목 설명·목표·계획이 대부분 채워져 있어 우선순위가 낮다. 매칭 방식 개선이 효과가 더 크다. 단, 자료가 얕은 연구실 재수집은 별도로 유효하다. |
| 겹치는 개념이 하나라도 있으면 모두 연관 과목으로 보여주는 현재 방식 | 일반 과목이 상위를 차지하고 핵심 과목이 밀려난다. 근거가 약한 과목도 섞여 들어온다. |

## 5. 열린 질문과 우려

- **외부 전송:** 검색 시 사용자 입력이 Anthropic API로 전송된다. 입력 화면 안내와 API 키 관리가 필요하다. 현재 앱에는 외부 API 호출이 없다.
- **도입 판단 근거:** AI 이해 단계가 정말 필요한지 수치로 확인하지 않았다.
- **싫어하는 주제의 처리:** 완전 제외와 순위 하향 중 무엇을 기본으로 할지 정하지 않았다.
- **심화 과목 범위:** 대학원 과목 데이터가 없어 심화 단계는 400번대까지만 보여줄 수 있다.
- **"도움이 된 과목" 수집:** 후기 폼과 선배 프로필 변경이 필요하다. 현재 커뮤니티 데이터는 더미다.

## 6. 다음 단계 제안

1. 부정·비교 표현이 들어간 관심 문장 약 20개로 테스트 세트를 만든다.
2. 현재 방식 / 부정어 규칙만 적용 / AI 이해 단계 적용, 세 가지를 비교해 AI 도입 여부를 결정한다.
3. 결정한 이해 방식 위에 `explanation` 필드와 화면을 구현한다.
4. 과목 점수·제외·이유 문장을 개선한다(데이터 변경 없이 가능).
5. `quote_ko` 생성·검토, 과목 단계별 묶기, 과목 고정/제외 필드, "도움이 된 과목" 수집 순으로 진행한다.
