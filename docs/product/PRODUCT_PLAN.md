## 1. 출발점과 방향 전환

3분커리의 출발점은 학생이 흩어진 교육·연구 정보를 연결하고, 관성적으로 익숙한 경로를 따르기보다 자신의 관심과 진로를 주도적으로 탐색하도록 돕는 것이다. 이 문제의식과 목적은 유지한다.

기존 기획은 교과목·연구실·학사 제도를 연결한 폭넓은 학술 로드맵을 지향했다. 새 개발에서는 연구참여 또는 연구실 진학을 고민하는 포스텍 학생의 연구실 선택에 먼저 집중한다. 과목 정보는 독립적인 수강 설계 서비스가 아니라, 연구실에서 할 수 있는 연구와 학생의 현재 준비도를 연결하는 재료로 사용한다.

‘3분’은 빠르고 간편한 경험을 뜻하는 브랜드명이다. 설문이나 전체 탐색을 실제 3분 안에 끝내야 한다는 요구사항은 없다. 핵심은 처음부터 많은 정보를 요구하지 않고 사용자가 구체적인 가치를 빨리 경험하게 하는 것이다.

## 2. 사용자와 제공 가치

### 우선 사용자

관심 있는 수업·주제 또는 진로 고민은 있지만, 이를 어떤 연구실과 연결할지 모르는 포스텍 학생을 우선 대상으로 한다. 이미 후보를 아는 학생도 추천 이유와 준비 가이드를 활용할 수 있다.

사용자는 반드시 전문 연구 분야명을 알고 있어야 하는 것은 아니다. 재미있었던 수업, 궁금한 현상, 해결하고 싶은 문제 등의 표현으로도 관심을 전달할 수 있어야 한다. 이러한 표현 방식 때문에 서로 다른 서비스 흐름을 만들지는 않는다.

서비스의 대상은 포스텍 학생이지만 현재 데이터가 포스텍의 모든 학과·연구실을 포함하는 것은 아니다. 초기 제공 범위를 실제 데이터 범위에 맞게 설명한다.

### 단기 가치

- 몰랐던 연구실이나 예상하지 못한 연결을 발견한다.
- 알고 있던 연구실도 자신과 연결되는 구체적인 이유를 이해한다.
- 해당 연구실에서 시도해볼 연구 방향과 필요한 준비를 파악한다.
- 여러 연구실을 하나씩 탐색하여 최종적으로 후보 2~3곳과 선택 이유를 정리한다.

첫 버전의 핵심 성공은 후보 압축이다. 연락·상담·연구참여 신청은 이후 가능한 행동이며, 첫 버전의 필수 완료 조건은 아니다. 후보 2~3곳은 사용자 목표이지 첫 결과를 무조건 3곳으로 제한하라는 뜻이 아니다.

### 장기 가치

추천에 대한 반응, 선택 이유, 실제 경험과 느낀 점이 쌓이며 사용자가 자신을 더 잘 이해하게 한다. 이를 바탕으로 더 정교한 선택지를 제공하고, 이후에는 연구실 외의 개인에게 맞는 정보로 확장한다.

MVP에서는 후보 저장과 짧은 메모가 그 출발점이다. 장기 경험 이력 분석과 자동 재추천을 먼저 구현하지 않는다.

## 3. 핵심 추천 원칙

### 관심·역량·선호를 구분한다

| 구분 | 의미 | 해석 원칙 |
|---|---|---|
| 관심·진로 | 알고 싶거나 앞으로 해보고 싶은 방향 | 직접 경험이 없어도 추천 근거가 된다. |
| 경험·준비도 | 수강 경험 등 현재 확보한 학습 근거 | 수강 여부를 숙련도와 동일시하지 않는다. |
| 선호 | 하고 싶은 연구 방식·경험·환경 | 사용자가 밝히지 않았거나 데이터가 없으면 단정하지 않는다. |

관심과 진로 연결을 기본으로 후보를 찾고, 연구 경험의 적합성과 참여 준비도를 함께 고려한다. 장기적으로 이를 여러 평가 축으로 표현하고 사용자 응답에 따라 중요도를 달리한다는 방향은 합의했다. 축의 정확한 수, 점수, 가중치 공식은 아직 확정하지 않았다. 현재 데이터로 확인할 수 없는 축을 임의의 수치로 채우지 않는다.

### 준비 부족으로 가능성을 닫지 않는다

관심과 선호에 잘 맞는 연구실은 준비가 부족해도 후보에 포함한다. 잘 맞는 이유와 보완할 준비를 함께 제시한다. 미수강을 자동 탈락 기준으로 삼지 않는다.

예: 사용자의 관심이 생명과학과 AI이고 현재 학습 근거는 AI에만 있더라도, AI를 생명과학 문제에 활용하는 연구실을 제안할 수 있다. 생명과학 관심은 유효한 추천 근거지만 생명과학 역량의 증거는 아니다. 실제로 두 분야를 연결하는 연구인지 연구실 자료에서 확인한다.

### 도메인과 방법론의 역할을 설명한다

관심 분야가 연구의 대상·문제인 도메인으로 쓰이는지, 문제를 해결하는 방법론으로 쓰이는지 구분해 연결 이유를 설명한다. 하나의 관심 분야가 둘 다로 작용할 수 있다.

예: 생명현상을 이해하기 위해 AI를 활용하는 연구와, 생명과학 데이터를 통해 AI 방법을 개발하는 연구는 사용자 관심과 연결되는 방식이 다르다. 데이터 근거가 있다면 여러 방향의 연구실을 첫 목록에 함께 제시한다.

확장 가능성이 있는 후보를 별도 버튼 뒤에 숨기지 않는다. 현재 경험을 이어가는 후보와 새로운 관심으로 확장하는 후보 모두 첫 결과에서 발견할 수 있어야 한다. 다양성만을 위해 관련성이 없는 후보를 억지로 넣지는 않는다.

### 확신의 근거와 불확실성을 함께 제공한다

추천은 ‘당신에게 객관적으로 최적인 연구실’이나 합격·참여 가능성의 보장이 아니다. 관심과 연결되는 근거, 현재 활용 가능한 지식, 추가 준비 및 확인할 점을 설명해 스스로 도전할 판단 근거를 제공한다.

연구실의 공식 요구사항과 서비스가 제안한 준비 항목, 실제 진행 중인 연구와 서비스가 제안한 탐색 주제를 구분한다.

## 4. 확정된 MVP 사용자 흐름

**관심·기본정보 입력 → 연관 연구실과 이유 확인 → 연구실 하나 선택 → 연관 교과목과 이유 확인 → 수강 과목 선택 → 최종 가이드 → 저장·메모 → 필요 시 다른 연구실 탐색**

### 1단계: 관심과 기본정보 입력

초기 입력을 간단하게 유지한다. 모든 수강 이력·역량·평가 축을 처음부터 묻지 않는다. 관심 표현 방식은 다양하게 허용하되 공통 흐름으로 처리한다.

이 단계에서 무엇을 기본정보로 받을지는 화면·입력 명세에서 결정한다. 학과·학년 등이 이미 필수로 합의됐다고 간주하지 않는다.

### 2단계: 연관 연구실과 추천 이유 제시

현재 데이터 범위에서 관심과의 연결을 설명할 수 있는 연구실을 목록으로 제시한다. 직접 연결과 확장 연결, 도메인·방법론의 역할을 이유에 담는다.

‘연관된 연구실을 모두 제안’한다는 의도를 유지한다. 초기 목록을 임의의 상위 2~3곳으로 고정하지 않는다. 목록의 정렬과 표시 방식은 UX에서 결정하며, 관련 없는 연구실이나 근거가 없는 추천은 포함하지 않는다.

처음 결과를 보이기 전에 선호를 완벽하게 분석하는 장시간 문답은 하지 않는다. 실제 후보를 보며 자신의 관심을 구체화할 수 있어야 한다.

### 3단계: 연구실 하나를 선택해 상세 탐색

한 번에 하나의 연구실만 상세 탐색한다. 선택은 최종 진학 결정이 아니라 해당 연구실을 더 알아보는 진입이다. 나중에 다른 연구실도 같은 흐름으로 탐색할 수 있다.

연구실별 상세 탐색은 사용자 가치 경험과 분석 비용을 관리하는 기본 단위다. 목록을 만들 때 모든 연구실의 개인별 최종 가이드까지 생성하지 않는다.

### 4단계: 도움이 되는 교과목 제시

선택한 연구실의 연구를 이해하거나 수행하는 데 도움이 되는 과목을 제시하고 연결 이유를 설명한다. 그다음 사용자가 그중 수강한 과목을 표시한다.

‘모든 과목’은 보유한 과목 데이터에서 연결 근거가 있는 과목 전체를 뜻한다. 학교의 모든 과목이나 공식 필수과목을 완전하게 제공한다고 주장하지 않는다. 필요한 경우 기본 지식과 더 깊은 연구에 도움이 되는 지식을 구분하되, 표시 방법은 후속 UX에서 정한다.

과목과 연구실을 연결할 때 코드나 담당교수만을 근거로 삼지 않는다. 연구 내용과 과목 설명·목표·진도계획 등 내용상의 연결을 설명할 수 있어야 한다.

### 5단계: 수강한 과목 선택

사용자는 제시된 과목 중 들은 과목을 선택한다. 선택한 과목이 없어도 탐색을 계속할 수 있어야 한다.

MVP에는 독학·프로젝트·수업 외 경험을 직접 적는 별도 입력을 넣지 않는다. 현재 준비도는 수강 정보에 한정된 추정이며, 과목을 듣지 않았다는 사실이 해당 지식이 전혀 없음을 뜻하지 않는다.

### 6단계: 최종 연구·준비 가이드

| 결과 | 사용자에게 설명할 내용 |
|---|---|
| 현재 시도해볼 만한 연구 주제 | 연구실과의 연결, 활용할 수 있는 수강 지식, 시작 방법, 예상 어려움과 확인할 점 |
| 추가 준비 후 도전할 연구 주제 | 필요한 지식, 관련 과목 또는 개인 학습 방향, 보완 후 시도할 방법과 예상 어려움 |

가능성과 난이도는 현재 자료와 수강 정보에 근거한 판단으로 설명한다. 합격 확률이나 연구 성공률을 임의의 백분율로 제시하지 않는다. 근거가 부족하면 판단의 한계를 밝히고 준비 가이드 중심으로 안내한다.

‘현재 시도’는 혼자 시작할 수 있는 탐색·학습 수준의 제안일 수 있으며 해당 연구실의 실제 참여 허가나 장비 접근 가능성을 보장하지 않는다. 근거 없이 진행 중인 프로젝트를 만들어내지 않는다.

연결할 수 있는 과목이나 연구 근거가 부족한 경우, 형식을 채우기 위해 주제와 준비 조건을 지어내지 않는다.

### 7단계: 저장과 짧은 메모

탐색한 연구실과 가이드, 선택 이유·느낀 점을 저장하고 다시 확인할 수 있게 한다. 여러 연구실을 하나씩 살펴본 뒤 후보 2~3곳을 남길 수 있도록 한다.

MVP의 비교는 저장한 정보를 다시 보며 선택하는 경험이다. 여러 연구실을 동시에 분석하거나 복잡한 비교 대시보드를 구현하는 요구사항은 아니다.

## 5. 비회원·로그인·과금 정책

| 행동 | 첫 버전 정책 |
|---|---|
| 관심 입력 및 연구실 목록·추천 이유 확인 | 로그인 없이 제공 |
| 첫 연구실의 상세 탐색 | 교과목·수강 선택·최종 가이드까지 전부 로그인 없이 제공 |
| 두 번째로 다른 연구실의 상세 탐색 시작 | 로그인 요청 |
| 로그인 후 이어가기 | 첫 탐색 결과와 입력을 유지하고 선택한 다음 연구실로 이어짐 |
| 과금·결제·크레딧 차감 | 첫 버전에 없음 |

첫 연구실을 다시 열거나 같은 연구실의 수강 선택을 수정하는 것은 다른 연구실을 새로 탐색하는 것으로 세지 않는 기본 해석을 사용한다. 실제 구현 명세에서는 익명 세션의 범위, 새로고침·실패 재시도, 로그인 취소, 저장 유지 기간을 명확히 정한다.

로그인 경계는 관심을 표현하거나 결과를 읽기 전이 아니라 첫 상세 탐색의 가치를 경험한 다음에 놓는다. 연구실 하나를 탐색하는 단위와 인증·향후 과금 정책을 분리해, 나중에 사업 정책이 바뀌어도 기본 흐름을 유지하도록 한다.

비회원 저장의 장기 유지나 기기 간 복원까지 합의된 것은 아니다. 첫 상세 탐색 전체를 막지 않으면서 저장·로그인 후 승계를 구현하는 방법은 인증·저장 설계에서 정한다.

## 6. MVP 포함·제외 범위

| MVP에 포함 | 후속으로 분리 |
|---|---|
| 간단한 관심·기본정보 입력 | 독학·프로젝트 경험 입력 |
| 연관 연구실 목록과 연결 이유 | 경험 이력 기반 자동 재추천 |
| 도메인·방법론 및 확장 가능성 설명 | 장기 자기 이해 대시보드 |
| 연구실 하나씩 상세 탐색 | 결제·크레딧·유료 구독 |
| 연관 과목 제시와 수강 표시 | 인터뷰·설문으로 연구 환경 정보 확충 |
| 현재/추가 준비 후 연구 주제와 가이드 | 연구실 외 정보 추천, 학교 범위 확대 |
| 후보 저장과 짧은 메모 | 종합 졸업 로드맵·자동 수강 이력 연동 |
| 두 번째 연구실부터 로그인 | 복잡한 다중 연구실 동시 분석 |

개인 학습 방향을 최종 가이드에서 제안하는 것은 MVP에 포함된다. 사용자에게 기존 독학 경험을 입력받는 것은 후속 기능이다. 두 가지를 혼동하지 않는다.

## 7. 데이터 기준과 한계

서비스 데이터는 [courses.jsonl](../../data/courses.jsonl)과 [labs.jsonl](../../data/labs.jsonl) 두 파일이다. 필드 의미와 사용 조건은 [데이터 README](../../data/README.md)를 따른다. 외부 원본 파일 없이 현재 두 파일의 내용을 기반으로 동작해야 한다.

| 데이터 | 현재 상태 | 사용 원칙 |
|---|---|---|
| 과목 | 419개 레코드 | 현재 기본 자료만 사용. 별도 POVIS 자료를 다시 합치지 않는다. |
| 연구실 | 교수 기준 65건 | `data_status == "collected"`인 60건만 추천 근거로 사용. 제외 5건은 추천하지 않는다. |
| 프로필(초안) | 개념 어휘 70개, 연구실 프로필 58곳, 과목 프로필 419건, 골드셋 25문장 | 추천 엔진의 입력. 사람이 검토하기 전에는 초안이며 인용문만 원문 검증됨. 상세는 [데이터 README](../../data/README.md). |

- 과목의 복합 코드 20건과 공동 연구실 기록은 한 행을 하나의 독립 선택지로 가정하기 어렵게 한다. 실제 후보 중복과 과목 선택 혼동을 막는 매핑을 구현 전에 검토한다.
- 연구실 자료는 전산·전자전기 및 일부 관련 분야에 집중돼 있다. 모든 관심 분야에서 적합한 후보를 찾을 수 있다고 가정하지 않는다.
- `quality_flags`와 `review_notes`는 정보 품질·확인 필요 사항이다. 학생과의 적합성 점수가 아니며, 정보가 부족한 연구실을 단순히 낮은 적합도로 해석하지 않는다.
- 과목의 수강 여부는 학습 경험의 단서이고 숙련도 검증은 아니다. 모집 안내도 현재 모집 상태의 보장이 아니다.
- 과목 출처 URL·학기와 자료의 수집 시점 등에 미확인 정보가 있다. 확인되지 않은 최신성을 주장하지 않는다.
- 사용자 진술, 수집 자료의 사실, 서비스의 추론·제안을 구분한다. 연구실 웹 근거를 가능한 범위에서 연결한다.
- 관련 자료가 없는 관심은 사용자 관심을 바꾸도록 유도하기보다 제공 범위의 한계로 설명한다.

## 8. 복잡도를 관리하는 개발 원칙

1. 하나의 공통 사용자 흐름을 유지한다. 관심 표현 방식이나 도메인·방법론 역할마다 별도 서비스 경로를 만들지 않는다.
2. 관심 입력 단계에서 수강 정보를 모두 수집하지 않는다. 연구실 선택 후 필요한 맥락에서 과목 선택을 받는다.
3. 목록용 연결 설명과 선택한 연구실의 상세 가이드를 분리한다. 전체 연구실에 대해 매번 개인화 상세 분석을 실행하지 않는다.
4. 데이터 해석·연구실 연결·과목 연결·가이드 생성·인증 및 저장의 책임을 구분한다. 이는 논리적 구분이며 별도 서비스나 복잡한 분산 시스템을 요구하지 않는다.
5. MVP 단계부터 결제 시스템이나 범용 커리어 플랫폼을 선행 구축하지 않는다.
6. 기술 선택은 제품 요구와 실제 품질·비용 검증에 따라 정한다. 이전 기획의 GraphRAG, 벡터 DB, 특정 모델·라이브러리는 채택된 요구사항이 아니다.
7. 생성 결과는 단순한 점수 순위보다 연결 근거와 다음 행동을 설명해야 한다. 개인화가 충분하지 않으면 정밀한 것처럼 표현하지 않는다.

## 9. 개발 순서와 단계별 확인

아래는 제품 관점의 개발 순서다. 실행 가능한 파일별 구현 계획은 기술·인터페이스 결정 후 별도로 작성한다.

| 순서 | 산출물 | 다음 단계로 넘어가기 전 확인 |
|---|---|---|
| 1. 데이터와 대표 시나리오 점검 | 연구실 식별·복합 코드 처리 규칙, 검토용 사례 | 제외 자료를 추천하지 않고 같은 연구실을 중복 노출하지 않는지 확인 |
| 2. 전체 흐름 프로토타입 | 입력→목록→단일 상세→과목 선택→가이드 화면 흐름 | 추가 기능 없이 핵심 흐름이 이어지고 초기 입력 부담이 과하지 않은지 확인 |
| 3. 근거 기반 연결 | 관심↔연구실, 연구실↔교과목 연결과 설명 | 실제 데이터에 연결 근거가 있고 도메인·방법론 및 확장 관심을 다루는지 확인 |
| 4. 준비 가이드 | 수강 선택을 반영한 두 갈래 연구 제안 | 수강 선택에 따라 설명이 달라지고 부족한 정보로 역량을 단정하지 않는지 확인 |
| 5. 인증·저장 통합 | 첫 탐색 비회원, 다음 연구실 로그인, 저장·메모 | 첫 결과 손실 없이 로그인과 다음 탐색이 이어지는지 확인 |
| 6. 사용자 검증 | 사용 관찰과 개선 항목 | 후보를 좁히고 이유·준비할 점을 설명할 수 있는지 확인 |

### 필수 검증 시나리오

- 연구 분야명 대신 재미있었던 수업이나 해결하고 싶은 문제로 관심을 입력해도 후보를 탐색할 수 있다.
- 생명과학·AI에 관심이 있고 AI 수강 근거만 있는 학생에게, 근거가 있는 확장 후보를 첫 목록에서 보여준다. 생명과학 역량을 보유했다고 설명하지 않는다.
- 관심이 도메인 또는 방법론으로 연결될 때 서로 다른 연결 이유를 설명한다.
- 관련 연구실이 없거나 자료가 부족하면 후보와 이유를 지어내지 않는다.
- 연구실 선택 전에는 모든 수강 이력을 요구하지 않는다. 선택 후에는 해당 연구실과 연결되는 과목을 이유와 함께 제시한다.
- 수강 과목이 하나도 없어도 진행 가능하며, 준비도 부족을 모든 연구실에 대한 자동 탈락으로 처리하지 않는다.
- 수강 과목이 일부·다수인 경우 최종 가이드의 활용 지식과 보완점이 실제 선택을 반영한다.
- 현재 시도할 주제와 추가 준비할 주제를 구분하고, 실제 연구실의 확정 프로젝트·공식 자격과 서비스 제안을 혼동하지 않는다.
- 수집 제외 항목, 과거 모집 공고, 공동 홈페이지, 복합 과목 코드의 품질 조건을 반영한다.
- 첫 상세 탐색은 로그인 없이 끝까지 가능하고 두 번째 다른 연구실에서 로그인한다. 로그인 실패·취소로 첫 탐색 정보가 사라지지 않는다.
- 저장한 연구실·가이드·메모를 다시 확인할 수 있다. 후속 기능인 독학·프로젝트 입력과 과금은 MVP에 나타나지 않는다.

### 사용자 검증에서 볼 것

핵심은 사용자가 후보 2~3곳과 선택 이유를 정리하고, 현재 시도할 일과 보완할 지식을 이해하는지다. 첫 가이드까지의 이탈, 두 번째 탐색 의향·로그인 전환, 후보 저장, 추천 이유의 납득도와 사실 오류도 함께 확인한다.

이는 검증 항목이지 이미 정해진 수치 목표가 아니다. 참여 인원·기간·전환율 목표·운영 비용 한도는 검증 계획에서 정한다.

| F. 학생 검증 | 4개 학과 학생 5명 이상 사용 관찰 | 후보 2~3곳 압축 여부, 추천 이유 납득도, 사실 오류 목록 확보 | 9절 '사용자 검증에서 볼 것' 기준 |
| G. 검색 확장 판단 | F의 결과에서 어휘 밖 표현 실패율을 측정한 뒤 임베딩 검색 도입 여부 결정 | 실패 사례 20건 이상에서 어휘 보강 대비 임베딩 이득이 확인될 때만 도입 | GraphRAG는 과목↔개념↔연구실 다단 설명이 필요해질 때 재검토 |
| H. 범위 확대 | 전 학과 수집과 프로필 작성 | 프로필 스키마·검토 도구·골드셋 형식을 변경 없이 재사용 | C·D 이후 |

이 계획은 제안이며 팀 논의로 순서를 바꿀 수 있다. 바뀌면 이 표와 결정 기록을 함께 갱신한다.

## 10. 구현 명세에서 확정할 사항

제품 방향을 문서화하기 위해 추가로 정할 핵심 흐름은 없다. 다만 아래 항목은 관련 구현을 시작하기 전에 구체화해야 하며, 이미 합의된 것으로 간주하지 않는다.

- 초기 기본정보의 항목, 관심 표현 UI, 필수·선택 입력 및 최소 입력 조건.
- 관심·경험·선호 평가 축의 정의, 사용자별 중요도 반영 방법, 후보 관련성·정렬 기준.
- 복합 과목 코드 및 공동 연구실 식별, 중복 처리와 데이터 부족 시 표시 방식.
- 최종 가이드의 주제 수, 난이도 표현, 근거 표시 및 재생성·수강 수정 동작.
- 로그인 수단, 익명 탐색의 유지 범위, 비회원 저장, 로그인 후 데이터 승계와 재시도 처리.
- 프론트엔드·백엔드·저장소·모델 등 기술 스택, 공통 분석의 재사용 범위, 호출 비용·응답시간 기준.
- 테스트 사용자 모집 범위, 검증 일정과 수치 목표.

## 12. 문서 유지 규칙

- 범위나 사용자 흐름이 바뀌면 이 문서의 해당 절을 먼저 갱신하고, 날짜·변경 이유를 남긴다.
- 구현 제안은 확정 요구사항과 분리한다. 논의한 아이디어를 승인 없이 MVP에 편입하지 않는다.
- 새 개발 작업은 관련 사용자 단계, MVP 포함 여부, 데이터 근거, 검증 시나리오를 확인하고 시작한다.
- 데이터 필드 변경은 데이터 README, 제품 행동 변경은 이 문서, 세부 기술 계약은 해당 구현 명세에 반영한다.
- 기존 v1 문서의 범위·기술·로드맵은 현재 문서와 충돌할 때 적용하지 않는다.

## 11. 커뮤니티 확장 (2026-10-01 결정)

MVP 흐름은 그대로 두고, 탐색 이후의 '경험 공유'와 '사람 연결'을 프로토타입으로 검증한다. 2절의 "연락·상담은 이후 가능한 행동"을 처음으로 구현하는 단계다. 결정 사항과 범위는 [커뮤니티 확장 계획](plans/2026-10-01-community.md)에 있다.

- 회원가입 시 이름·별명·이메일·학교·관심 분야를 필수로 받는다(10절 '초기 기본정보' 항목 중 계정 프로필 부분을 확정). 관심 입력 화면의 첫 탐색은 여전히 로그인 없이 가능하다.
- 연구참여 후기는 자기 신고 기반이며 연구실의 공식 정보나 모집 여부가 아니다. 참여 사실 확인 수단은 후속이다.
- 대학원생 선배는 정보 공개에 동의한 사람만 노출하고, 연락은 웹 내 쪽지로 한다. 실제 선배 모집(이벤트 동의)은 후속이다.
- 현재 후기·선배·대화는 모두 더미 데이터(`dummy` 표시)이며 사용자 검증 전에 실제 데이터 수집 방식과 함께 교체한다.
